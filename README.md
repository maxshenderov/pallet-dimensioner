# pallet-dimensioner

> Измерение габаритов паллет (длина, ширина, высота) двумя ортогональными веб-камерами —
> верхняя (top, сверху вниз) и боковая (side, горизонтально). Стабилизация по серии кадров,
> отправка события в REST API WMS.

Самостоятельный сервис для локального хоста (Raspberry Pi / mini-PC) рядом с постом измерения.
Источник: `ТЗ_Две_камеры_измерение_паллет.md`.

## Принцип измерения

- **Камера top** — footprint (длина × ширина) как bounding box контура, перевод из пикселей в мм
  через гомографию по 4 ArUco-маркерам (плоскость пола).
- **Камера side** — высота и одна видимая сторона паллеты, через 1-2 ArUco-маркера.
- **Коррекция перспективы**: высота от камеры side используется для пересчёта масштаба
  camera top (объект ближе к камере → выглядит крупнее, чем есть).
- **Кросс-проверка**: сторона от камеры side сравнивается со стороной camera top после
  коррекции; расхождение сверх допуска → `cross_check_passed: false`.

Подробности формулы — в ТЗ, раздел 2; реализация — `src/vision/dimensions.py`.

## Структура

```
config/post_config.yaml   — конфигурация конкретного поста (камеры, ROI, HSV, допуски)
src/
  main.py                 — основной цикл
  calibration/            — калибровка объектива (chessboard) + ArUco-гомография
  capture/                — захват синхронизированных кадров с двух камер
  vision/                 — сегментация, расчёт габаритов, стабилизация
  integration/            — отправка события в REST API (retry + буферизация на диск)
  models.py               — pydantic-модели события и конфигурации
scripts/
  calibrate_post.py       — интерактивная калибровка поста (ROI/HSV трекбары, детекция ArUco)
  accuracy_test.py        — прогон серии измерений против эталона, вердикт пригодности
tests/                    — юнит-тесты на синтетических данных (без физических камер)
```

## Запуск

### Docker (продакшн, пост измерения)

```bash
cd services/pallet_dimensioner
cp .env.example .env
# отредактируй CAMERA_TOP_DEVICE / CAMERA_SIDE_DEVICE в .env под /dev/videoN хоста
docker compose up -d
```

Перед первым запуском камеры должны быть откалиброваны (см. ниже) — результат сохраняется в
`config/camera_intrinsics_top.json` / `_side.json`, которые монтируются вместе с `config/`.

### Локально (разработка / калибровка)

```bash
cd services/pallet_dimensioner
pip install -r requirements-dev.txt
python -m src.main
```

### Тесты

```bash
pytest -q
```

27 юнит-тестов на синтетических/фикстурных данных — `vision/`, `calibration/`, `integration/`
покрыты независимо от физических камер (per ТЗ раздел 9). `capture/camera_stream.py` и
`main.py` тестируются только вручную на реальном посту.

## Калибровка поста

1. **Объектив** (разово, на каждую камеру): нафотографировать шахматную доску (`CHESSBOARD_SIZE =
   (9, 6)` внутренних углов) под разными углами, прогнать `calibrate_lens()` →
   `config/camera_intrinsics_{top,side}.json`.
2. **ROI и HSV-пороги фона**: `python scripts/calibrate_post.py top` (или `side`) — live-превью
   с трекбарами, `a` — проверить детекцию ArUco, `s` — сохранить в `post_config.yaml`.
3. **Проверка точности**: `python scripts/accuracy_test.py --length 1200 --width 800 --height
   1450` — серия измерений эталонного объекта, вердикт «пригодно» при систематической ошибке
   ≤ 30 мм и std ≤ 15 мм (допуски конфигурируются в `post_config.yaml`).

## Формат события (`POST /api/v1/pallet-measurements`)

```json
{
  "post_id": "POST-04",
  "timestamp": "2026-08-18T10:23:41Z",
  "length_mm": 1195,
  "width_mm": 800,
  "height_mm": 1487,
  "cross_check_passed": true,
  "cross_check_delta_mm": 8,
  "samples_count": 12,
  "measurement_method": "dual_webcam_ortho"
}
```

`measurement_method` явно указывает источник — на других постах может стоять лазер/depth-камера
(см. основное ТЗ WMS-проекта, `ТЗ_Система_измерения_высоты_паллет.md`, разделы 4.3-4.4).

При сетевом сбое событие буферизуется на диск (`data/pending_events/`) и досылается при
следующем успешном соединении.

## Известные ограничения / что не входит в этот сервис

- Сопоставление измерения с конкретной паллетой (штрихкод/RFID) — на стороне FastAPI-бэкенда.
- Обучение ML-модели сегментации — не требуется, пока классическая HSV-пороговая сегментация
  справляется; отдельная задача при необходимости.
- Изменения в 1С и основном FastAPI-сервисе — вне этого репозитория.
